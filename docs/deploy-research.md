# Continuous deployment: which approach? (research, 2026-11-01)

The question: what is the best way for a merge to `main` to update the running Docker Compose stack without the owner SSHing in, for this repo as it is now (public) and if it were private? This note compares the current pull timer ([deploy.md](deploy.md), `scripts/deploy.sh`), the push "doorbell" that is being added (job `notify` in `.github/workflows/release.yml`, `deploy-hook/`, `deploy/homelab-deploy.path`), and the other options.

**How each claim was checked.** The sandbox could not open docs.github.com, tailscale.com, komo.do, doco.cd, docs.portainer.io, coolify.io, argo-cd.readthedocs.io or fluxcd.io (the proxy refused them). Claims were checked in one of three ways, and each is labelled:

- **[src]**: read in the project's own docs or source repository, cloned on 2026-11-01. The link is the published page; the repo and commit are listed below.
- **[index]**: read only in the search-engine text of the official page. Treat as likely, not confirmed word for word.
- **unverified**: no primary source found, or it is my own reasoning.

Repos and commits read: [github/docs](https://github.com/github/docs) `33b1f4a`, [tailscale/github-action](https://github.com/tailscale/github-action) `064b105` (= v4.4.0, the version `release.yml` pins), [tailscale/tailscale](https://github.com/tailscale/tailscale) `49aa9c8`, [argoproj/argo-cd](https://github.com/argoproj/argo-cd) `7d3f650`, [fluxcd/website](https://github.com/fluxcd/website) `74d6a37`, [fluxcd/source-controller](https://github.com/fluxcd/source-controller) `236b223`, [fluxcd/flux2](https://github.com/fluxcd/flux2) `3fa784e`, [moghtech/komodo](https://github.com/moghtech/komodo) `780ac68`, [kimdre/doco-cd](https://github.com/kimdre/doco-cd) `10e14d3` (latest tag v0.99.1), [portainer/portainer-docs](https://github.com/portainer/portainer-docs) `3e1ec1e`, [louislam/dockge](https://github.com/louislam/dockge) `0329dab`, [coollabsio/coolify-docs](https://github.com/coollabsio/coolify-docs) `5d951ba`, [containrrr/watchtower](https://github.com/containrrr/watchtower) `ca0e86e`.

## TL;DR

- **Public repo (now): keep pull + doorbell, which is what is being built.** Pull-only is already the right security model: nothing in GitHub holds a key to the house. The doorbell keeps that property, because it carries no authority: `deploy.sh` still re-checks the `release` check run and deploys only that sha. It cuts latency from 3 to 4 minutes down to well under a minute (my estimate, unverified), and the hourly timer catches every missed ring. This "webhook plus slow poll" shape is exactly what Argo CD and Flux recommend. One improvement: switch the Tailscale step from an OAuth secret to **workload identity federation**, so GitHub stores no long-lived Tailscale secret.
- **Self-hosted runner: no for public.** GitHub itself says to use self-hosted runners only with private repos, because fork PRs can run code on the runner.
- **SSH from Actions: no.** Tailscale SSH has no forced-command option, and here tailscaled runs in a container, not on the host. A forced-command OpenSSH key works but puts a door key in GitHub for no gain over the doorbell.
- **Ready-made tools: none is better here.** None of them gate on a CI check run, so they would deploy a commit before its `sha-<commit>` image exists. Their GitHub webhooks need a public URL, and most need the Docker socket plus an admin UI. **Watchtower is archived (December 2025) and unmaintained.** doco-cd is the closest fit if you ever want to drop the custom script.
- **Private repo: same design**, with a fine-grained read-only token and a deploy key on the host (already documented as Task 32). A self-hosted runner becomes acceptable on a private repo, but it still needs a fallback for when the host is offline, and it adds a long-running agent. On GitHub Free, a private repo gets **no branch protection or rulesets**, so `main` cannot be protected. That matters more than the choice of trigger.

## Findings

### What "normal" looks like: poll, plus a webhook to go faster

- **Argo CD** polls Git every 3 minutes by default: "120 seconds + up to 60 seconds of jitter". It says setting polling to 0 and relying on webhooks alone "is not recommended … failure of webhooks due to network issues, misconfiguration etc.", and suggests "a lower-frequency interval … for example `15m`, `1h`" when you use webhooks [src] ([Argo CD FAQ](https://argo-cd.readthedocs.io/en/stable/faq/), `docs/faq.md`; [argocd-cm.yaml](https://argo-cd.readthedocs.io/en/stable/operator-manual/argocd-cm-yaml/) `timeout.reconciliation: 120s`).
- **Flux** is "by design **pull-based**". Webhook receivers make "**pull-based** pipelines as responsive as **push-based** pipelines", and the webhook guide's example sets the Git source interval to `60m` [src] ([Flux: webhook receivers](https://fluxcd.io/flux/guides/webhook-receivers/)). `spec.interval` is required on a GitRepository, with `5m` in the examples [src] ([GitRepository spec](https://fluxcd.io/flux/components/source/gitrepositories/#interval)), and `flux bootstrap` defaults to `--interval 1m` [src] ([flux2 `cmd/flux/bootstrap_github.go`](https://github.com/fluxcd/flux2/blob/main/cmd/flux/bootstrap_github.go)).

So the current 3-minute timer matches the Argo CD default, and the doorbell plus a 1-hour timer matches what both projects recommend once a webhook exists.

### (1) Pull timer (current)

- Nothing connects in; the server makes outbound HTTPS calls only ([deploy.md](deploy.md#security-model)).
- On a public repo, the check-run API needs no token. Unauthenticated REST calls are limited to "60 requests per hour" per IP [src] ([REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-unauthenticated-users)). The script calls the API only when `origin/main` has moved (`scripts/deploy.sh`, step 4), so polling every 3 minutes stays well under it.
- Weak point: 3–4 minutes of latency ([deploy.md](deploy.md#limits)). Nothing else.

### (2) Push doorbell over Tailscale (being built)

- **How the Action joins.** `tailscale/github-action` takes an OAuth client with the writable `auth_keys` scope and at least one tag; its nodes "are marked as Ephemeral … and log out immediately after finishing their CI run" and are pre-approved under device approval [src] ([github-action README](https://github.com/tailscale/github-action#readme); [Tailscale GitHub Action docs](https://tailscale.com/docs/integrations/github/github-action) [index]). The tags passed must match the tags on the credential [index] (same page).
- **No stored Tailscale secret is possible.** The action also supports **workload identity federation**: `oauth-client-id` plus `audience`, no `oauth-secret`, and the job needs `permissions: id-token: write`; it requires Tailscale 1.90.1 or later [src] ([README, Workload identity federation](https://github.com/tailscale/github-action#workload-identity-federation); [Tailscale KB 1581](https://tailscale.com/kb/1581/workload-identity-federation), not opened). GitHub's OIDC subject for a push to `main` is `repo:OWNER/REPO:ref:refs/heads/main`. Repos created after 15 July 2026 use an immutable `repo:OWNER@ID/REPO@ID:...` format, and older repos keep the old format unless they opt in [src] ([OIDC reference](https://docs.github.com/en/actions/reference/security/oidc#filtering-for-a-specific-branch)). Tie the federated identity to the `main` subject, so a workflow on any other branch cannot join the tailnet. Exactly how Tailscale matches the subject is unverified (KB not opened).
- **Blast radius if GitHub leaks everything.** The policy in the contract grants `tag:ci` only `tcp:9000` on `tag:homelab`. The receiver also needs a valid HMAC with a ±300 s timestamp. Even with both, the attacker can only make `deploy.sh` run, and it deploys only a `main` sha whose `release` check (from the `github-actions` app) succeeded (`scripts/deploy.sh`, step 4). The worst case is an extra no-op run. Unverified: that the `notify` job's `permissions: {}` would need `id-token: write` added for WIF.
- **Fork PRs never see the secrets.** "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository" [src] ([Events that trigger workflows, forked repos](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)). `notify` also runs only on `push` to `main` (`release.yml`).
- **Failure modes.** A lost ring (host offline, the `tailscale` or `caddy` container restarting in the middle of a deploy, Tailscale down) costs at most an hour, because the timer is the fallback. `notify` does not affect the `release` check, so the gate is unchanged (`release.yml` comment).
- **Cost.** GitHub-hosted runners are free on public repos [src] ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). On a private repo, Free includes $12 a month of compute, about 2,000 Linux minutes at $0.006 [src] (same page). A `notify` job uses well under a minute per merge (unverified estimate).
- **Possible simplification (not needed):** replace the HMAC with a GitHub OIDC token the hook verifies. That removes `DEPLOY_HOOK_SECRET`, but RS256 verification is not in Python's standard library, so the receiver would need a dependency. With the tailnet ACL already limiting who can reach `:9000`, the HMAC is enough (my judgment).

### (3) Self-hosted runner on the host

- **Public repos: GitHub says no.** "We recommend that you only use self-hosted runners with private repositories. This is because forks of your public repository can potentially run dangerous code on your self-hosted runner machine by creating a pull request that executes the code in a workflow" [src] ([Add self-hosted runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)). Self-hosted runners "can be persistently compromised by untrusted code in a workflow" [src] ([Secure use, hardening for self-hosted runners](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners)).
- **The approval gate is not a defence.** By default only first-time contributors need approval, and "a user that has had any commit or pull request merged … will not require approval". GitHub warns that with self-hosted runners "potentially malicious user-controlled workflow code will execute automatically if the user is allowed to bypass approval … or if the pull request is approved" [src] ([Managing GitHub Actions settings for a repository](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)). Here the runner user is in the docker group, which is root-equivalent ([deploy.md](deploy.md#security-model)).
- **Private repos: acceptable.** For PRs from forks of a private repo, "workflows only run when they are enabled" [src] ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)). The options ("Run workflows from fork pull requests", "Send secrets …", "Require approval …") are settings you turn on [src] (repo Actions settings page above). Only people with access to a private repo can fork it (unverified for personal accounts; for organizations, forking private repos must be allowed by an owner [src] ([Managing the forking policy](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/managing-the-forking-policy-for-your-repository))).
- **Host offline.** A job with no online runner "will remain queued until a runner comes online", and "If the job remains queued for more than 24 hours, the job will fail" [src] ([Self-hosted runners reference](https://docs.github.com/en/actions/reference/runners/self-hosted-runners); [Actions limits](https://docs.github.com/en/actions/reference/limits): "Job queue time | 24 hours"). After that nothing retries, so you still need a timer fallback.
- **Other facts.** The runner needs only outbound HTTPS on 443 [src] (self-hosted runners reference). It updates itself when a job is assigned, or within a week of a release [src] (same page). It is removed if it has not connected for 14 days [src] ([reusable `self-hosted-runner-auto-removal`](https://github.com/github/docs/blob/main/data/reusables/actions/self-hosted-runner-auto-removal.md)). Self-hosted runner usage is free and does not draw from included compute [src] ([Actions billing, compute allowance](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
- **One real plus for private repos.** In a job, `GITHUB_TOKEN` can publish packages of the workflow repo [src] ([Working with the Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)), so a runner job could `docker login ghcr.io` with a token that expires with the job instead of keeping a classic PAT on the host. GitHub Packages "only supports authentication using a personal access token (classic)" outside Actions [src] ([About permissions for GitHub Packages](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages)). This repo already avoids the host token with `RACK_SOURCE=build` ([deploy.md](deploy.md#public-vs-private-repo)).

### (4) A GitHub Action that SSHes in over Tailscale

- **Tailscale SSH cannot restrict the command.** The policy action has `Accept`, `Reject`, `HoldAndDelegate`, `SessionDuration`, agent and port forwarding, and recorders, but no command restriction [src] ([`tailcfg.SSHAction`](https://github.com/tailscale/tailscale/blob/main/tailcfg/tailcfg.go)). Rules are `accept` or `check`, and `check` re-authenticates a human, which a CI node cannot do [index] ([Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)). So a CI node would get a full shell as the target user (docker group = root).
- **It also does not fit this host.** tailscaled runs inside the `tailscale` container in userspace mode (`compose.yml`, `TS_USERSPACE=true`). Tailscale SSH there would land in that container, not on the host. Using it would mean installing tailscaled on the host (unverified reasoning; not tested).
- **Forced-command OpenSSH key** (`command="…/deploy.sh",restrict` in `authorized_keys`, [sshd(8) AUTHORIZED_KEYS](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT), not opened from here) can limit the key to running `deploy.sh`. It is then functionally the doorbell, but with an SSH private key stored in GitHub and sshd exposed on the tailnet. The doorbell gives the same result with a smaller surface.
- **Same offline problem** as (3): a failed job is not retried.

### (5) Ready-made GitOps tools for Compose

Common problem: **none documents gating on a CI check run.** `deploy.sh` waits for `release` because `compose.yml` pins `RACK_TAG=sha-<commit>`, and that image exists only after `release` pushes it. A tool that deploys on the commit would deploy before the image exists, or would build it on the server. Second problem: a native **GitHub webhook comes from the internet**, and this host is tailnet-only, so you would need a public endpoint (Funnel or a tunnel) or a GitHub Action that joins the tailnet, which is the doorbell again.

- **doco-cd.** "Lightweight, declarative GitOps … deploys and updates Docker Compose projects … using polling and webhooks", a distroless image [src] ([README](https://github.com/kimdre/doco-cd#readme)). Default poll interval `180s` (minimum 10 s); polling "does not require doco-cd to be reachable from the internet" [src] ([Poll settings](https://doco.cd/latest/Poll-Settings/)). It mounts `/var/run/docker.sock` [src] ([App settings](https://doco.cd/latest/App-Settings/)). Rollback is "Push a revert commit, that is the normal path", and moving the branch back is skipped as stale [src] ([Migrating from Docker Compose](https://doco.cd/latest/Migrating-from-Docker-Compose/)). It can report commit status back to GitHub [src] ([Git settings](https://doco.cd/latest/Git-Settings/#commit-status-reporting)), but I found no option to wait for a check run (unverified that none exists). Actively maintained (commit on 2026-11-01, v0.99.1).
- **Komodo.** Git-sourced stacks are cloned onto the host and "you can use webhooks to auto-redeploy on push" [src] ([Komodo: Compose stacks](https://komo.do/docs/deploy/compose)). The webhook validates `X-Hub-Signature-256`; "If Komodo is on a private network, set up a public proxy for `/listener` requests" [src] ([Komodo: Webhooks](https://komo.do/docs/automate/webhooks)). Image auto-update needs a rolling tag such as `:latest`, runs from a daily procedure, and the docs suggest Renovate for pinned tags [src] ([Komodo: Automatic updates](https://komo.do/docs/deploy/auto-update)). Core needs MongoDB or FerretDB [src] ([Komodo: Setup](https://komo.do/docs/setup/)). It is a full platform (Core + Periphery + database + UI), which is more than one stack needs.
- **Portainer GitOps.** A stack from Git can update by **Polling** ("Fetch interval") or by a **Webhook** URL "for example via GitHub actions" [src] ([Portainer: Add a stack](https://docs.portainer.io/user/docker/stacks/add)). It compares the latest commit hash with its database and runs `docker-compose up` in its own clone. It "doesn't otherwise reference any other files in the repository, unless those files are referenced by the compose files", which "can have consequences if you are trying to build an image" [src] ([How do automatic updates work?](https://docs.portainer.io/faqs/troubleshooting/stacks-deployments-and-updates/how-do-automatic-updates-for-stacks-applications-work)). No health-gated rollback is documented. The default fetch interval and whether every option is in the Community Edition are unverified.
- **Dockge.** A compose file manager with an editor, terminal and "Update Docker Images". Its README lists **no Git sync or webhook** feature [src] ([Dockge README](https://github.com/louislam/dockge#readme)). It is not a CD tool.
- **Coolify.** Auto-deploy via a GitHub App, GitHub Actions or a repo webhook [src] ([Coolify: GitHub auto deploy](https://coolify.io/docs/applications/sources/github/auto-deploy)). The GitHub App needs a "public Coolify URL" or "a domain exposed through a tunnel" [src] ([Coolify: GitHub App](https://coolify.io/docs/applications/sources/github/app)). "Coolify uses SSH to manage the servers connected to it", including localhost [src] ([Coolify: OpenSSH](https://coolify.io/docs/core/infrastructure/servers/openssh)). It is a PaaS that would take over proxying and the stack layout. Too big a change for this repo.
- **Watchtower + registry.** **Archived and unmaintained.** The README says "⚠️ This project is no longer maintained" (commit `ca0e86e`, 17 December 2025) [src] ([containrrr/watchtower README](https://github.com/containrrr/watchtower#readme)). The repo was archived on 17 December 2025 [index] ([GitHub repo page](https://github.com/containrrr/watchtower)). The default poll was 24 hours [src] ([docs/arguments.md](https://github.com/containrrr/watchtower/blob/main/docs/arguments.md)). It only updates images, not compose files or scripts, and it needs the Docker socket. A community fork, `nickfedor/watchtower`, is cited as a drop-in replacement [index] (search results only, not checked). Not a fit: it would replace pinned `sha-` tags with floating tags and drop the gate and rollback.

### (6) Other current options

- **Tailscale Funnel + a native GitHub webhook** (`check_run` or `workflow_run` event) to the hook: this would remove all Tailscale credentials from GitHub. But the hook would then be on the public internet, protected only by the webhook HMAC. The doorbell's private, tag-limited path is the better trade (my judgment; Funnel details not verified here).
- **Workload identity federation for the doorbell** (above) is the one 2026 change worth adopting now.
- **Renovate** to bump pinned image tags by PR, so the `:latest` apps also go through PR → CI → deploy. Komodo's docs point to it [src] ([Komodo: Automatic updates](https://komo.do/docs/deploy/auto-update)). This is separate from the trigger question.

### Private repo specifics

- **`main` cannot be protected on GitHub Free.** Protected branches and rulesets are available "in public repositories with GitHub Free … and in public and private repositories with GitHub Pro, GitHub Team, …" [src] ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches); [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)). Every approach above runs whatever lands on `main`. On a private Free repo, nothing forces PRs or CI before a push to `main`. The `release` gate still blocks a red commit, but not a direct push of a bad but green commit. Use GitHub Pro, or only push to `main` from your own account with 2FA.
- **Tokens on the host.** For the gate, use a fine-grained, read-only token (Checks, Contents, Metadata), and fetch with a read-only deploy key ([deploy.md](deploy.md#public-vs-private-repo)). A GHCR pull from outside Actions needs a classic PAT with `read:packages` [src] (packages permissions page above), which is why `RACK_SOURCE=build` exists. Fine-grained token expiry limits were not checked (unverified): set a reminder to rotate it.
- **Actions minutes** are now billed against $12 a month of included compute on Free [src] (billing page above). CI + release + notify per merge is small, but no longer zero.

## Recommendations

**Public repo (current): keep pull + doorbell. The doorbell being built is the right call.** It is the Argo CD/Flux pattern (fast trigger, slow poll as a safety net). It keeps the property that nothing in GitHub can make the server run unchecked code. It reuses the tested `deploy.sh` gate and rollback. Do these alongside it:
1. Move `notify` to workload identity federation: drop `TS_OAUTH_SECRET`, add `id-token: write` to that job only, and bind the federated identity to the `main` subject.
2. Keep the ACL to `tag:ci` → `tag:homelab:9000` only, and keep the hourly timer. Do not set it to "never" (Argo CD's own warning).
3. Leave the `release` gate in `deploy.sh` as it is. It is what makes the doorbell safe.

**Private repo: the same design.** Add the read-only token and deploy key (Task 32), and use `RACK_SOURCE=build` or a classic `read:packages` PAT. A self-hosted runner is a reasonable alternative only on a private repo, and only if you are happy to run an always-on agent with docker-group rights. It still needs the timer, for the 24-hour queue limit. It is not better than the doorbell, so do not switch. Fix branch protection first (GitHub Pro, or accept the risk knowingly).

**Ready-made tool?** No, not now. None gates on the `release` check, so with `sha-` pinned images they would race the image build. All of them add a privileged service, and those with UIs add a login to protect. If you ever want to delete `deploy.sh`, **doco-cd** is the one to try (polling, no UI, maintained), with images switched to a tag that exists before the commit lands on `main`. Avoid Watchtower (archived).

### What would change my mind

- **You want more than this one host or stack** (several machines, many repos, a UI for others): Komodo or doco-cd becomes worth its weight.
- **The repo goes private on Free and you would rather not hold any long-lived token on the host**: a private-repo self-hosted runner, which uses a job-scoped `GITHUB_TOKEN` for GHCR, starts to look better. Keep the timer.
- **Deploys must happen within seconds and are frequent**: still the doorbell; just lower the fallback interval.
- **Tailscale is removed from the setup**: drop the doorbell, keep the 3-minute timer. Do not open a public webhook just to save 3 minutes.
- **A tool adds "wait for check run" gating plus health-based rollback for Compose**: re-evaluate doco-cd against `deploy.sh`.
- **GitHub changes the fork-PR rules for public repos** so that workflows cannot target self-hosted runners without explicit opt-in: re-check option (3). Today it is a clear no.
